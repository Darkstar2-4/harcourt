# Files, ajax and search endpoints: deliberate differences from the PHP oracle

- `scs_file.php?content_id=`: Rust serves content to every viewer who may see what owns it (a family's files to accounts that may browse that family, portal content to that portal's accounts and to staff, documents, pages and heroes to anyone) and does not check the second field of the id, the sign-in time of the PHP session that rendered the link. The oracle answers `Content missing: <id>` to a link from another session and to every request without a PHP session, so a signed-in viewer who may see the content gets it from Rust where the oracle says `Content missing`. The echoed id is HTML-escaped.
- `scs_file.php` resizes images with the `image` crate, not GD: a resized image has the PHP's size and type, not its bytes.
- `scs_file.php` serves nothing by name (`code`, `filename`, `type`). Without `content_id` it answers what the oracle answers when the named file is missing: 500 with an empty body, or an empty 200 with `watermark`.
- `scs_ajax.php` answers the search box (as live hxweb did) and, for active Internal-and-above accounts, `table=user&source=company_name` and `table=inventory&detail=sku`. Every other request gets the oracle's refusal, a 401 with an empty body, where the oracle may answer data or a PHP error.
- The search box labels suggestions in the language of the page it is on (`/catalogue/` or `lang=fr` is French) and scopes them by the Rust visitor on every request. Live hxweb took both from the PHP session, which the oracle reports as English for every persona tried, and used an empty scope when the request carried no PHP session cookie.
- `image_viewer.php` answers 410 (retired.rs); no page links it.
